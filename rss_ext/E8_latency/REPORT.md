- eager에서 정수 경로는 작은 계산(5M·19M, N 512, 48M N 512)에서 Python의 Triton 실행 지연에 묶인다. forward마다 kernel 7개를 띄우고 LayerNorm·Mish를 손 kernel로 한다.

- **E7 재현**
  - E7(RTX A5000, 학습된 5M 체크포인트, eager-step N 512)에서 int det/fp32는 +17.7%(int4 그릇판)였다.
  - 이번 A40에서는 E7 kernel이 **+10.9%**, 새 일반 경로가 **+27.6%**다.
  - 즉 "5M·N 512·eager에서는 정수 kernel이 fp32보다 느리다"는 E7의 결과가 재현된다. 크기는 장비와 kernel 수에 따라 다르다.
- **E7 융합 kernel 대 새 일반 경로**
  - graph에서는 E7 kernel이 새 일반 경로보다 20~33% 느리다. E7 kernel은 512폭 행 전체를 한 block에서 GEMM과 융합한다(block 16행). 그래서 program 수가 적고 tensor core 활용이 낮다.
  - eager N ≤ 2048에서는 E7 kernel의 시간이 새 경로보다 25% 짧다. forward당 kernel 수가 적어 Python 실행 지연이 적다.
- E7 kernel의 dither 오버헤드(graph +3~4%)가 새 경로(+0.4~2%)보다 크다. E7처럼 모든 program이 u를 직접 그리기 때문이다(PLAN §4.3과 같은 원인).

## 3. 논문(RSS)에 주는 의미

1. **E7 약점의 정체**: E7의 "정수 kernel이 fp32보다 18% 느림"은 저비트 산술의 한계가 아니다. 작은 모델(5M)·작은 배치(N 512)를 eager로 돌린 실행 방식의 결과다.
   - CUDA graph로 world-model rollout을 재생하면(TD-MPC2도 `compile=True`일 때 planner를 CUDA graph로 돌린다) 같은 W8A4 정수 경로가 모든 크기·N에서 fp32보다 1.9~3.3배 빠르다.
   - 12칸 중 10칸에서는 TF32·BF16 중 빠른 쪽보다도 1.19~1.48배 빠르다(L1·L2). 나머지 두 칸은 317M N 8192 1.08배, 5M N 2048 0.95배다.
2. **dither는 사실상 공짜다(L3)**: 공유 dither(sh-iter)의 추가 지연은 graph에서 −0.2~+2.1%, eager-step에서 +0.5~+1.5%다.
   - 층·forward마다 Philox u 벡터 하나를 그리면 된다. 모든 후보가 그 u를 공유하므로 후보 수와 무관하다.
   - E7처럼 모든 program이 u를 직접 그려도 +3~4%다.
3. **쓸 수 있는 문구(제안, 주장 변경은 사용자 승인 사항)**: "On an Ampere A40 with CUDA-graph execution, the W8A4 integer world model is 1.9–3.3× faster than FP32 and up to 1.5× faster than TF32/BF16 at 5M–317M parameters, and shared dither adds ≤ 2.1% latency."
   - 함께 밝힐 것: §4의 1, 2, 5. BF16 기준선은 autocast(호출마다 가중치 변환)다. 층 0은 fp32다. 계획 step 전체(eager)의 이득은 317M에서 0.74배다.
4. **E10과의 연결**: E10의 317M은 이 측정에서 정수 kernel 이득이 가장 큰 크기다(fp32 대비 0.31~0.35, min(fast) 대비 0.76~0.93). E10에서 손상과 처방이 재현되면 "kernel이 실제로 이득인 크기에서도"라고 쓸 수 있다. E10 설계 §3.7 문구와 맞는다.
5. **Blackwell(E8b, 기술)**: 317M의 4096폭 층에서 NVFP4 GEMM은 BF16보다 최대 5.3배 빠르다(M 8192). int8은 3.0배, FP8은 1.9~2.0배다.
   - FP4 활성 양자화의 확률적 반올림(sh-iter)은 PyTorch 연산 구현에서 RNE(det)보다 오히려 2~14% 싸다. "dither가 공짜"라는 결론이 FP4 형식에도 이어질 근거다.
   - 단, 융합된 FP4 양자화 kernel이 없으면 양자화 연산이 GEMM의 약 20배라 실제 이득은 융합 kernel이 있어야 나온다.

## 4. 위험과 한계

1. **BF16 기준선의 불리함**: 설계(E7과 같음)의 BF16은 autocast라서 호출마다 가중치를 bf16으로 바꾼다.
   - 미리 bf16으로 바꾼 모델이면 BF16이 더 빠를 수 있다. 특히 큰 모델·작은 N에서 그렇고, L2 여유가 줄어든다(317M N 8192는 이미 0.927).
   - TF32는 이런 불리함이 없다. int-det/tf32는 5M N 2048(1.057)을 빼면 0.68~0.84다.
2. **층 0은 fp32(설계)**: 정수 경로의 층 0(입력 [z, a] → 폭) GEMM은 fp32다. 큰 모델에서 정수 경로 시간의 상당 부분을 차지하므로, 정수 경로에는 보수적이다.
3. **장비 의존**: A40(GA102) 하나, pod 하나다. A40은 300 W 상한에 자주 걸렸다(63%). 무거운 칸의 비율은 이 전력 상한 아래의 값이다. 다른 GPU(능동 냉각 A5000, H100, Blackwell)에서는 비율이 다를 수 있다. 같은 칩의 다른 장비로 반복 측정하지는 않았다.
4. **무작위 가중치**: 지연은 값과 무관하다는 설계 전제를 따랐다. 다만 전력 상한 구간에서는 데이터에 따른 전력 차가 clock에 영향을 줄 수 있다. 공식 초기화의 reward head 0 가중치도 그대로다. 학습된 체크포인트와 수치가 약간 다를 수 있다.
5. **측정 범위**
   - graph-WM은 world-model rollout만이다. encoder, π, Q, MPPI 표본·top-k는 빠져 있다.
   - 계획 step 전체는 eager로만 쟀다(eager-step). 계획 step 전체를 CUDA graph로 잡은 측정(TD-MPC2 compile 경로)은 하지 않았다.
6. **결과를 보고 고른 구현 세부(본 측정 전, PLAN §4.3에 기록)**
   - dither u를 한 kernel 앞에서 한 번 그리는 방식: 처음 구현은 약 +5%였다.
   - row kernel tile 1개: det 시간으로 고름. dither에는 보수적이다.
   - 이 선택은 smoke 측정을 보고 했다. 판정에 쓴 본 측정은 그 뒤 고정된 구현으로 했다.
   - E7식(program마다 u를 그림)이면 오버헤드는 +3~4%(E7 kernel, 5M)다. 그래도 L3 문턱 5% 안이지만, 317M에서 E7식은 smoke에서 약 +5%였다.
7. **eager 측정은 호스트 잡음에 민감**: 공유 호스트의 load가 튀었다. eager·step의 개별 block은 최대 +15% 흔들렸다. 판정(graph)은 영향이 없었다.
8. **정확성 점검의 범위**: 이번 E8은 단일 forward·rollout 수준의 수치 동일성만 확인했다(fake-quant 기준과 코드 불일치 ≤ 3.8e-6). 폐루프 성공률은 E7(같은 수치 경로)의 결과에 기댄다.

## 5. 편차

1. tf32의 범위를 dynamics·reward 호출로 한정했다(설계 §1.3 "encoder·Q·π는 fp32"). eager-step에만 영향이 있다. (PLAN §9)
2. bf16 autocast를 `cache_enabled=False`로 했다(graph 캡처용, 하는 일은 같음). (PLAN §9)
3. sh-iter 난수
   - seed 식은 device counter식이고 u는 한 kernel 앞에서 한 번 그린다(PLAN §3).
   - E7 kernel은 device seed로 바꾼 복사본이다(graph 재생에 필요).
   - 난수 값은 E7과 다르다(일정은 같음).
4. smoke를 두 번 돌렸다(구현 수정 2건, PLAN §4.3). 본 측정과 판정은 v2 구현이다. v1 결과는 `results/smoke_v1/`에 있다.
5. 지연 측정은 공식 초기화(reward head 0)를 그대로 썼다. 정확성 점검의 reward만 head를 다시 무작위로 채운 복사본이다. eager-step 관측은 무작위 고정 열이다(환경 없음).
6. 분석
   - 판정과 §2의 [기술] 항목은 본 측정 전에 쓴 `e8_analyze.py` 그대로다.
   - [사후] 표시 항목은 결과를 본 뒤 맥북에서 결과 JSON만 읽어 계산했다: 짝 오버헤드의 절대 ms, step 대비 WM 몫, 전력 상한·호스트 load spike 영향.
7. E8b: 이미지에 numpy가 없어 표준 라이브러리로 바꿨다. FP4 양자화 graph 단계는 두 번 고쳐 다시 돌렸다. MXFP4 GEMM은 지원되지 않아 오류만 기록했다(§7, LOG).

- **MXFP4 미지원**: torch 2.9.1 `_scaled_mm`의 block 1×32(e8m0) scale은 float8 operand(MXFP8)만 받는다. "Invalid scaling configuration" 오류를 기록했다.

### 7.2 FP4 활성 양자화 연산: det 대 sh-iter, (M, 4096) fp32 fake-quant

- E9 정의(DESIGN_ext §2.3)를 PyTorch 연산으로 구현했다.

| 형식 | M | eager det / sh-iter ms (sh-iter 추가) | CUDA graph det / sh-iter ms (sh-iter 추가) |
|---|---|---|---|
| NVFP4 | 512 | 0.449 / 0.421 (−6.3%) | 0.134 / 0.128 (−4.3%) |
| NVFP4 | 2048 | 0.969 / 0.845 (−12.7%) | 0.848 / 0.753 (−11.2%) |
| NVFP4 | 8192 | 5.224 / 4.521 (−13.5%) | 5.152 / 4.482 (−13.0%) |
| MXFP4 | 512 | 0.447 / 0.418 (−6.5%) | 0.131 / 0.129 (−2.1%) |
| MXFP4 | 2048 | 0.967 / 0.828 (−14.4%) | 0.841 / 0.745 (−11.3%) |
| MXFP4 | 8192 | 5.194 / 4.497 (−13.4%) | 5.140 / 4.455 (−13.3%) |

- sh-iter(열마다 u 하나, 행 공유, 매 호출 새로 뽑음)가 det보다 싸다. det의 동률 처리(짝수 가수 쪽 RNE)가 비교·논리 연산을 더 쓰기 때문이다. u 생성(열 4,096개)은 무시할 만하다.
- 수치 점검(M 512): 상대 오차 NVFP4 det 0.095 · sh-iter 0.137, MXFP4 0.115 · 0.158. 평균 편향은 둘 다 |bias| ≤ 5e-5다.
- 융합되지 않은 PyTorch 연산 구현이라, M 8192에서 양자화 1회(약 4.5~5.2 ms)가 NVFP4 GEMM(0.25 ms)의 약 20배다. 실제 배치에는 융합된 양자화 kernel이 필요하다. 이번에는 설계대로 짜지 않았다.
